# 運用手順書（障害対応）

`docs/PRODUCTION_RELEASE_CHECKLIST.md` 9.3節に基づく、公開後の代表的な障害対応手順。
網羅的な手順書ではなく、まず何を見て・何をすればよいかの最短経路をまとめたもの。

## 1. Railwayで直前のデプロイへ戻す

1. Railwayダッシュボード → 対象サービス → `Deployments` タブを開く。
2. 直前に正常だったデプロイを選び、`Redeploy` を実行する。
3. `/health` が200を返すこと、続けて `/ready` が200を返すこと（DB接続まで含めて健全か）を確認する。

**注意**: アプリのロールバックはコード・実行プロセスを戻すだけで、DBのスキーマは戻らない。
DB migration（`src/migrations/`）を伴うリリースをロールバックする場合、新しいmigrationで
追加した列・テーブルを古いコードが参照しないか確認する。基本的にはmigrationは
後方互換になるよう作る（既存列の削除・型変更を避ける）ことでロールバックを安全にする。

## 2. PostgreSQLバックアップから復元する

1. 復元作業の前に、まず**現状のDBの手動バックアップを取得する**（誤った復元からも戻れるようにするため）。
2. RailwayのPostgresサービス → `Backups` から復元したい時点のバックアップを選び、復元を実行する
   （またはRailwayが提供する接続情報を使い、ローカルから `pg_restore` で復元する）。
3. 復元後、`/ready` でDB接続を確認し、主要なAPI（`/temples`、`/next-bus`、`/weather-proxy` 等）が
   正常に応答することを確認する。
4. GTFSデータやGoogle Places由来データなど、バックアップ時点より新しいデータがあれば、
   3節の手順で再取り込みが必要か確認する。

## 3. Google APIキー漏えい時の交換

1. Google Cloud Console → 該当プロジェクト → 「認証情報」で、漏えいしたキーを**即座に無効化**する
   （削除ではなく、まず無効化してから作業する方が安全）。
2. 新しいキーを発行する。ブラウザ用（`GOOGLE_MAPS_BROWSER_API_KEY`）とサーバー用
   （`GOOGLE_MAPS_SERVER_API_KEY`）は分離して発行し、それぞれに適切な制限をかける
   （ブラウザ用はHTTPリファラー制限、サーバー用はAPI種別制限、可能ならIP制限）。
3. Railwayの環境変数を更新し、再デプロイする。
4. 新キーで本番動作（地図表示、`/temple-photo/:no` の写真表示）を確認してから、
   無効化した旧キーを完全に削除する。

## 4. 気象庁データ取得失敗時の確認箇所

1. `curl https://www.data.jma.go.jp/developer/xml/feed/regular_l.xml` で気象庁側のフィード自体が
   応答するか確認する（気象庁側の障害の可能性を切り分ける）。
2. 本番の `/weather-proxy?points=<札所番号>,<YYYY-MM-DD>,<HH:MM>` を実際に叩き、
   `available:false` になっていないか確認する。
3. `src/jma-weather.ts` の `feedCache`/`reportCache` はプロセス内メモリキャッシュのため、
   プロセス再起動でキャッシュがクリアされる（再起動が応急処置になる場合がある）。
4. 対象日が予報範囲外（短期予報は0〜2日、週間予報は3〜7日）でないか、
   `src/data/temple_jma_areas.json` の札所→予報区域の対応が壊れていないかを確認する。

## 5. GTFSデータ更新失敗時の戻し方

1. GTFS取り込みスクリプト（`src/import-gtfs.ts` 等、事業者ごとの取り込み処理）は
   agency_key単位でテーブルへ書き込む。失敗時は失敗した事業者のデータだけが
   不完全になっている可能性があるため、まず対象agency_keyを特定する。
2. `gtfs_stops`/`gtfs_routes`/`gtfs_trips`/`gtfs_stop_times` 等を対象agency_keyで
   `SELECT COUNT(*)` し、明らかに0件・件数が異常な事業者がないか確認する。
3. 前回の正常データに戻す必要がある場合は、2節のバックアップ復元を使うか、
   問題のagency_keyの行だけを削除して該当事業者のGTFS ZIPを再取り込みする。
4. `src/precompute-cross-agency-stops.ts`（事業者間の乗り換え停留所ペア事前計算）は
   `CrossAgencyStopLink` エンティティが `src/data-source.ts` の `entities` に登録されておらず、
   このデータソースでは実行時にエラーになる可能性がある。GTFS更新後にこのスクリプトを
   使う運用がある場合は、別途対応が必要（本ドキュメント作成時点では未対応の既知の問題）。

## 6. 障害告知を掲載する場所

現時点で専用のステータスページは無い。障害が発生した場合の現実的な選択肢:

- `/privacy` や `/credits` と同様の静的ページ（例: `/status`）を一時的に用意し、
  障害内容・復旧見込みを掲載する。
- Google Playのストア説明文やアプリ内お知らせ欄（実装があれば）を一時的に更新する。
- 利用者への直接の連絡手段が無いため、再発防止のためにも外部監視（9.1節）による
  早期検知を優先する。
